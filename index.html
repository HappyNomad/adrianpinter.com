AI engineer. Context engineering for agents that hold up in production.

Most AI agents don’t fail because the model is weak. They fail because of what the model was given:

  • what it knows when it starts,
  • which tools it can reach,
  • and whether anyone measures what it does.

That’s where I work. I’m an AI engineer who builds agents that hold up on real work, and I design their context from how models actually process text, not from prompt tricks.

At Diebold Nixdorf, I helped build and ship a production LLM agent that helps service technicians troubleshoot banking and retail devices. I worked on its tool calling, multi-agent coordination and retrieval, and designed the evals that kept it honest: generated ground truth scored for groundedness, relevance and accuracy, plus guardrails against hallucination, PII leakage and prompt injection.

Since then, my most demanding client has been my own life. I wrote agent skills that run on Claude over my Documents folder, on real data, every day:

  • Every session starts already knowing where each part of my life stands.
  • It checks what’s due or overdue across everything and names the one thing to do first.
  • It takes in email in bulk: deduplicates it, files it, pulls out attachments, and updates my notes with whatever changed.
  • It cuts big, avoided problems down to one step I can finish today.

Now I’m building a harness for apps made entirely of prose and configuration, with no app code. An app starts as instructions a model carries out, and each part hardens into configuration once daily use shows it has to run the same way every time. Any model can plug in, and the data stays on the user’s own disk.

What agent engineering has taught me:

  • An agent is only as good as the documents it wakes up with.
  • If you can’t measure it, you can’t ship it.
  • Start in prose; make a part deterministic only once real use proves it needs to be.

I got here through decades of production software, most of it in C# and .NET: enterprise work for Travelport, Prudential and Geisinger, and a point-of-sale system I designed and built for the Thai restaurant I co-owned. Thirteen years of running that restaurant left me with no patience for technology that doesn’t solve a real problem for the person using it.

I’m not tied to one stack anymore. With coding agents doing much of the typing, the language matters far less than the design, the evals and the judgment, so I use whatever the problem calls for.

I’m open to AI engineering roles, full-time or contract, and to conversations with teams building agents.
